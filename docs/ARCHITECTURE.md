# Архитектура Payvan

## Слои

```
UI (Compose-экраны)  →  ViewModel-и (AuthViewModel, ChatViewModel) и ChatSession
                     →  PayvandApi (интерфейс, модуль core)
                     →  SupabaseApi (реализация: Auth, PostgREST, Realtime, Storage)
                     →  Supabase: PostgreSQL + RLS
```

- `core` — чистый Kotlin без Android. Весь обмен с сервером здесь, поэтому он проверяется обычными JVM-тестами
  против настоящего сервера.
- `app` знает только интерфейс `PayvandApi`. Реализация создаётся в одном месте — `AppContainer`.
- `ChatSession` — общее состояние вошедшего пользователя: список бесед, кэш профилей, realtime-события,
  отметка «в сети» раз в минуту, локальные уведомления.

## Данные

| Таблица | Содержимое |
|---|---|
| `profiles` | публичный профиль: Payvan ID (`PV` + 8 цифр, выдаётся триггером, неизменяем), имя пользователя, имя, аватар, last_seen |
| `profile_private` | телефон (виден только владельцу) |
| `conversations` | личные чаты, группы, каналы; признак публичности |
| `members` | участники, роли owner / admin / member, отметки `last_read_at` и `last_delivered_at` |
| `messages` | текст, вложение, ответ, пересылка, отметки правки и удаления |
| `blocks`, `reports`, `device_tokens` | блокировки, жалобы, push-токены |

Статусы сообщения: «отправлено» — сервер сохранил строку; «доставлено» — устройство получателя обновило
`last_delivered_at`; «прочитано» — получатель открыл чат (`last_read_at`). Идентификатор сообщения создаёт клиент,
поэтому повторная отправка после обрыва связи не создаёт дубликат.

## Безопасность

- **Права проверяет сервер.** На всех таблицах включён RLS; сообщения и файлы видят только участники беседы.
  Изменения бесед, участников и ролей идут только через серверные функции, которые проверяют роль вызывающего.
  Прямые UPDATE/DELETE сообщений запрещены.
- **Подделка запросов.** `sender_id` обязан совпадать с пользователем из токена; системные сообщения создаёт только
  сервер; путь файла обязан лежать в папке беседы и отправителя. Это покрыто тестом с «сырыми» REST-запросами.
- **Ключи.** В APK только публичный anon-ключ. Сборка и экран подключения отклоняют ключ `service_role`.
  Секреты push хранятся в секретах Edge Functions.
- **Сессия** шифруется AES-256-GCM ключом из Android Keystore; резервное копирование данных приложения отключено.
- **Транспорт.** Релизная сборка разрешает только HTTPS/WSS.
- **Ограничение частоты.** Не более 20 сообщений за 10 секунд и 60 в минуту на пользователя (триггер в БД),
  не более 20 новых групп в час; лимиты входа и писем — на стороне Supabase Auth.
- **Блокировки и жалобы.** Заблокированный не может писать в личный чат, не находит пользователя в поиске
  и не может добавить его в группу. Жалобы попадают в таблицу `reports` (просмотр — через панель Supabase;
  отдельной панели модератора пока нет).
- **Сквозного шифрования нет.** Сообщения защищены при передаче (TLS) и правилами доступа, но администратор сервера
  технически может их прочитать. В приложении это написано прямо. Правильный путь к E2EE — протокол Signal
  (библиотека libsignal) с ключами устройств и подтверждением отпечатков; это отдельный большой этап.

## Работа при плохой связи

- Неотправленное сообщение остаётся в чате со статусом ошибки и отправляется повторно по нажатию.
- Realtime переподключается автоматически; после восстановления список чатов и открытый чат перечитываются.
- Обновление токена без сети не разлогинивает пользователя.
- Фото сжимаются до 1600 px перед отправкой; скачанные вложения кэшируются; видео, файлы и голосовые
  загружаются только по нажатию.
- Чего нет: локальной базы для чтения переписки совсем без сети (см. STATUS.md).

## Звонки (спроектировано, не реализовано)

Кнопок звонка в интерфейсе нет намеренно: вкладка «Звонки» честно сообщает о статусе.

1. **Медиа:** WebRTC (сборка libwebrtc для Android). Аудио — Opus, видео — VP8/H.264. Шифрование DTLS-SRTP встроено.
2. **Сигнализация:** обмен SDP offer/answer и ICE-кандидатами через Realtime Broadcast в канале пары пользователей;
   запись о звонке — в новой таблице `calls` под RLS.
3. **NAT:** STUN бесплатен, но за мобильными операторами (CGNAT) значительная часть соединений требует
   **TURN-ретранслятор**. Это единственное, что нельзя получить «из ничего»: либо свой coturn на VPS,
   либо облачный TURN (у некоторых провайдеров есть бесплатные квоты — проверять перед выбором).
4. **Входящий звонок:** data-push FCM высокого приоритета → экран звонка через `ConnectionService`/full-screen intent.
5. **Групповые звонки:** mesh работает до 3–4 человек; дальше нужен SFU-сервер (например, self-hosted LiveKit).

Порядок внедрения: аудио 1-на-1 → видео → групповые через SFU.

## Переезд на собственный сервер

Supabase — открытое ПО. Варианты по возрастанию усилий:

1. **Self-hosted Supabase** (Docker Compose на VPS): применить те же миграции, перенести базу `pg_dump`/`pg_restore`
   и файлы хранилища, сменить адрес сервера в сборке. Код приложения не меняется.
2. **Свой backend:** написать другую реализацию `PayvandApi` (например, Ktor + PostgreSQL + WebSocket).
   UI и ViewModel-и не затрагиваются; схема базы и SQL-функции переносятся как есть.
